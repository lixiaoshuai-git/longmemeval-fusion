## 1. 预备知识

### 1.1 什么是大语言模型（LLM）

大语言模型（Large Language Model，LLM）是一个接收文本、输出文本的函数。
输入一段文字，输出一段文字，中间的计算在 GPU 上完成。本项目使用的模型是
GLM 系列（glm-5.2），通过 HTTP API 调用：程序把文本发给服务器，服务器把
生成的文本返回。

调用时的三个关键参数：

| 参数 | 含义 | 本项目的取值 |
|---|---|---|
| `temperature` | 控制输出的随机程度。0 表示每一步都选概率最高的词，输出基本可复现 | 0 |
| `max_tokens` | 输出长度的上限。token 是模型处理文本的最小单位，约等于 0.75 个英文单词 | 按调用点不同（10–900） |
| `n` | 生成几个候选 | 1 |

**非确定性来源**：即使 `temperature=0`，同一输入两次调用的输出仍可能不同。
原因是服务端 GPU 并行计算的浮点求和顺序不固定，导致概率并列时选择不同。
实测影响：同一份代码同一批题，两次全量运行有 37/500 题的答案翻转（约
±1.4pp 准确率波动）。这个数字是后续所有「要不要保留某个改动」判断的基础。

### 1.2 提示词（prompt）

提示词是发给 LLM 的完整输入文本。本系统的每个 LLM 调用点都有一段固定的
模板文字（写在代码里，不随数据变化），模板中留有占位符，运行时把具体的
对话内容、日期填进去。提示词的质量直接决定 LLM 输出的格式是否可解析。

### 1.3 JSON 与 JSONL

- JSON：一种文本格式，用 `{ "键": "值" }` 表示结构化数据。LLM 的结构化
  输出要求它按 JSON 格式回答，程序才能解析。
- JSONL：每行一个独立 JSON 对象的文本文件，本项目用它存评测结果
  （每行一道题的记录）。

**实际遇到的坑**：glm-5.2 在「逐候选输出 JSON 对象」的任务上，有时不输出
标准数组 `[ {...}, {...} ]`，而是逐行输出裸对象（JSONL 形态）。因此解析
函数 `extract_json_array` 同时兜住三种形态：标准数组、截断数组的宽松修复、
逐行裸对象流。这是「LLM 输出形态必须在解析器兜住」这条教训的来源。

### 1.4 缓存（cache）与内容寻址

一次 LLM 调用耗时 1–15 秒、花费真实费用。本项目把每次 LLM 调用的结果存进
一个 JSON 文件（缓存文件），键（key）是「提示词前缀版本号 + 输入内容的
哈希值」。下次遇到相同输入，直接读缓存，不再调 API。

关键设计：**缓存键绑定提示词版本号**（`PROMPT_VERSION = "fusion-v2.4"`）。
改了提示词就必须手动升版本号，否则会错误命中旧提示词的缓存；升了版本号，
该类调用的旧缓存全部失效、需要重新生成——这个代价在每次改提示词前都要
评估（实测一次全量关系缓存重生成会引入 ±1.5pp 的随机波动，见第 10 节）。

### 1.5 LongMemEval 基准

这是本系统接受的考试。数据集由多轮对话（会话）组成，每个会话里有 user
和 assistant 两种角色的发言。每道题包含：若干个会话（带日期）+ 一个问题
（带提问日期）+ 标准答案。

三个难度档：

| 档位 | 每题包含 | 特点 |
|---|---|---|
| Oracle | 只有问题相关的会话（2–6 个，约 2–6k token） | 证据已筛选好 |
| S | 相关会话 + 大量干扰会话（约 122k token） | 需要从噪声里找证据 |
| M | 介于两者之间 | |

七个题型：multi-session（跨会话聚合，如「我一共买了几盆植物」）、
temporal-reasoning（时间推理，如「两次参观隔了几天」）、knowledge-update
（知识更新，如「我现在住在哪」，答案会随时间变化）、single-session-user
（答案在某条 user 发言里）、single-session-assistant（答案在 assistant
发言里）、single-session-preference（偏好推荐类）、`_abs` 后缀（拒答类：
标准答案是「信息不足」，考察系统会不会在证据缺失时硬答）。

两个角色：

- **reader（答题模型）**：拿到「记忆上下文 + 问题」生成答案。
- **judge（判分模型）**：拿到「问题 + 标准答案 + 系统答案」判对错。
  本项目用 glm-5.2 代跑 judge；官方 judge 是 gpt-4o。语义审计显示
  glm-5.2 代跑的判错集合中约 64% 是误判（答案语义正确但措辞不匹配）。

## 2. 问题定义

### 2.1 LLM 是无状态的

LLM 的每次 API 调用互相独立。昨天告诉它「我买了 3 盆植物」，今天问它
「我有几盆植物」，它不知道——除非把昨天的对话原文放进今天的输入。
对话历史不会被自动保存。

### 2.2 全上下文方案及其问题

最直接的做法：把所有历史对话原文塞进每次答题的输入。这就是「全上下文
基线」（full-context baseline）。它在 Oracle 档测得 87.90 ± 0.84。

三个问题：

1. **成本**：输入长度与费用成正比。S 档单题 122k token，全上下文方案
   每题答题成本极高。
2. **噪声**：S/M 档的干扰会话会把不相关内容混进输入，稀释模型注意力。
3. **合规**：本项目所属计划的手册附录 F.1 明确禁止把全上下文作为交付
   实现（因为那等于没有做记忆系统），只允许作为对照上界探针。

记忆系统的目标：**把长历史压缩成小而准的上下文，在 Oracle 档追平上界，
在 S 档用 8.4 倍压缩保持可用精度。**

### 2.3 记忆系统的输入输出定义

- 输入（写入期）：一个会话（若干条 user/assistant 发言）+ 会话日期。
- 输入（查询期）：一个问题 + 提问日期。
- 输出（查询期）：一段「记忆上下文」文本，交给 reader 作答。

## 3. 系统总览

### 3.1 双层记忆

| 层 | 内容 | 特点 |
|---|---|---|
| 事实层 | 从对话中抽取的原子事实（Event 对象），带时间结构 | 有损压缩，但结构化、可做算术、可做版本管理 |
| 证据层 | 对话轮次原文（Evidence 对象），逐字保留 | 无损，保底召回用 |

两层都进最终上下文。事实层负责「结构化可计算」，证据层负责「细节不丢」。

### 3.2 四个 LLM 边界

整个系统只有四处调用 LLM，其余全部是普通 Python 代码：

| # | 位置 | 任务 | 为什么必须用 LLM | 为什么只在这里用 |
|---|---|---|---|---|
| 1 | 写入期·抽取 | 从一句对话里列出原子事实 | 理解自然语言 | 输出是结构化 JSON，后续全可计算 |
| 2 | 写入期·关系分类 | 判断新事实与旧记忆的关系 | 语义判断（同义改写识别） | 决策结果喂给确定性代码执行 |
| 3 | 查询期·解析 | 把问题转成结构化查询计划 | 理解问题意图 | 计划喂给确定性执行器 |
| 4 | 查询期·作答 | 基于上下文回答 | 生成自然语言 | 官方答题模板，不可更改 |

时间计算、计数、求和、排序、过滤、去重、拒答判定、前提校验、渲染——
全部是 Python 代码。这样做的理由：这些任务 LLM 会出错且错误不可复现，
代码做则结果可单测、可复现、可审计。

### 3.3 模块文件对照

| 文件 | 职责 |
|---|---|
| `memory_sys/schema.py` | Event/Slot/MemoryStore 数据模型与确定性存储算子；`append_event` 是唯一构造点 |
| `memory_sys/fusion.py` | 组合根：缓存、生命周期、对外 API（行为由三个 mixin 提供） |
| `memory_sys/write_path.py` | 写入期流程（抽取 / 定时 / 关系 / 落库） |
| `memory_sys/read_path.py` | 查询期流程：`read()` 编排 + `_plan()` 解析 + `_render()` 算子渲染 + `_guard_sections()` 守卫 |
| `memory_sys/render.py` | 上下文渲染与守卫（台账 / 偏好 / 摘录 / 地板 / 拒答） |
| `memory_sys/temporal.py` | 相对时间规则解析与合法性校验 |
| `memory_sys/options.py` | 运行时选项（实例级开关，不可变） |

| `scripts/judge.py` | 判分（直接使用官方判分提示词） |
| `cli.py` | 交互入口（REPL） |
| `tests/` | 104 例离线单元测试 + CLI 手工测试用例 |

## 4. 数据模型（逐字段）

### 4.1 Event：一条原子事实

```python
@dataclass
class Event:
    subject: str          # 谁的事实："user" 或 "assistant"
    predicate: str        # 关系类别：acquire / live_in / prefer / ...
    value: str            # 值："peace lily" / "Berlin" / ...
    category: str         # 类别：plant / place / money / ...（25 个封闭值）
    valid_from: datetime|None   # 事实从何时开始为真
    valid_to: datetime|None     # 事实到何时不再为真；None = 现在仍为真
    tx_seq: int                 # 写入顺序号（全局递增）
    status: str                 # active | superseded | invalidated | archived
    amount: float|None          # 事实中的数值（金额/数量/时长）
    date_text: str              # 用户原话的时间表述（回显给作答 LLM）
    corrects: bool              # 是否为更正（"实际上我记错了"）
    stated_at: datetime|None    # 陈述时间（= 会话日期）
    evidence: list[(会话id, 轮次号)]   # 这条事实出自哪些轮次（溯源指针）
    fact: str                   # 完整事实原句（数字/专名逐字保留）
    slot_id: int|None           # 槽位簇 id（语义聚类键）
```

一个真实例子的完整生命周期：

> 用户在 2023-05-10 的会话里说："I got three new peace lilies for my
> living room."

抽取输出（LLM 返回的 JSON 数组的一项）：

```json
{"fact": "The user got three new peace lilies for their living room.",
 "when_raw": "", "when": "2023-05-10",
 "category": "plant", "kind": "event"}
```

存入后（Event 对象的字段值）：

```
subject="user"  predicate="acquire"  value="peace lily"
category="plant"  valid_from=2023-05-10  valid_to=None
amount=3.0  fact="The user got three new peace lilies..."
evidence=[("s2", 4)]  status="active"
```

### 4.2 双时间轴：两个时间戳回答两个不同的问题

| 时间戳 | 符号 | 回答的问题 | 例子 |
|---|---|---|---|
| `valid_from` / `valid_to` | τ_v（有效轴） | 这个事实**在现实世界里**什么时候成立？ | 「我 2022 年住 Berlin，2023 年搬到 Munich」→ Berlin 的 τ_v 是 2022-01 到 2023-01 |
| `stated_at` | τ_t（陈述轴） | 这句话**是什么时候说的**？ | 上面那句话是 2023-01-05 说的 → τ_t = 2023-01-05 |

区分两条轴的原因：有些陈述在陈述时刻就揭示了过去的事实（「我上周买了
一盆植物」在 5 月 10 日说，购买发生在 5 月 3 日）。只有 τ_v 一条轴时，
「买之前我有没有这盆植物」这类问题无法回答。

### 4.3 演化与更正的几何语义（本系统最核心的设计）

当同一个 `(subject, predicate)` 出现新值时（如居住地从 Berlin 变成
Munich），两种情况的处理完全不同：

| 情况 | 用户的话 | LLM 判定 | 代码执行 |
|---|---|---|---|
| **演化**（evolve） | 「我搬到 Munich 了」 | 旧值到新锚点前**曾经为真** | 旧 Event 的 `valid_to` 设为新值的 `valid_from`（只封 τ_v），状态改 `superseded` |
| **更正**（correct） | 「更正一下，其实我住的是 X」 | 旧值**从未为真**（当时说错了） | 旧 Event 状态直接改 `invalidated`，不设 `valid_to`（τ_v、τ_t 两轴都封） |

两者的可观察差别：`value_at(t)`（查历史时刻的值）对 `superseded` 的旧值
**仍然返回**（2022 年问「我住哪」答 Berlin 是对的），对 `invalidated`
的旧值**永远不返回**（说错的话在任何时刻都不算真）。

### 4.4 Slot 与两个查询算子

`Slot` 是同一个 `(subject, predicate)` 下所有 Event 的集合（按
`valid_from` 排序）。两个查询算子：

- `current()`：在 status=active 的事件里取 `valid_to` 右端点最大者。
  回答「**现在**怎么样」。
- `value_at(t)`：取「`t` 落在其有效区间内、且状态不是 invalidated」的事件。
  回答「**t 时刻**怎么样」。

### 4.5 谓词基数与冲突判定

每个 predicate 有一个基数属性（`PREDICATE_CARD`）：

- **单值（cardinality=1）**：同一时刻只能有一个值为真，如 `live_in`、
  `work_at`、`age`。新值写入时触发 4.3 的几何冲突处理。
- **多值（cardinality=2）**：可以同时存在多条，如 `acquire`（买了 3 盆
  就是 3 条独立事件）、`visit`、`prefer`。新值写入不触发版本闭合。

封闭谓词表（40 个词）是去重的前提：如果谓词开放，「buy」「purchase」
「got」会被当成三种不同关系而无法合并。

**写入去重**：`(subject, predicate, 归一化value)` 三元组相同的 active
事件直接合并（只追加证据指针，不新建）。归一化 `norm_value` 做的事：
转小写、去虚词、`lilies→lily`（-ies→y）、`lugs→lug`（去尾部 -s）。

## 5. 写入期流程（六步）

输入：一个会话（`[{"role": "user", "content": "..."}, {"role":
"assistant", "content": "..."}, ...]`）+ 会话日期字符串。

### 5.1 证据入库

所有轮次原样存入证据层（`Evidence` 列表），这一步没有任何 LLM 参与。

### 5.2 user 轮次逐条抽取

对每条 user 发言，取它后面紧邻的 assistant 发言作为**仅供理解的上下文**
（提示词里明确「从 assistant 发言里什么都不要抽」），调用 LLM。

提示词的七条硬规则（`TURN_EXTRACTION_PROMPT`，逐条解释）：

1. **原子事实句必须自足且数字/量词/价格/时长/专名逐字保留**——因为后续
   问题可能问那个精确数字（「38 枚 1920 年前的美国硬币」不能写成
   「一些古币」）。
2. **一句话 = 一条**。两件事不能合并成一条。
3. **获取规则**：只要出现「买了/收到/得到某物」，必须独立成一条
   `kind="event"` 的事实，即使那句话主要在说别的。
4. **时间解析**：相对时间按会话日期换算（"two weeks ago" → 会话日期
   减 14 天）；`when_raw` 必须逐字抄用户原词；没有时间线索才允许
   `none`；模糊词（recently）原样放进 `when_raw`，不许猜日期。
5. **预购规则**：预购/预订的「获得时间」是到货日期，不是下单日期。
6. **kind 四分类**：`state`（会变化的持续状态：住址、工作、收藏总数）、
   `event`（一次性事件：买了、参观了、出生）、`preference`（喜欢/讨厌/
   偏好）、`numeric`（挂在事件上的数量）。
7. 闲聊、问候、对 assistant 的提问、assistant 的回复一律跳过；没有
   可抽取内容输出 `[]`。

输出示例（JSON 数组，每项一个原子事实）。

### 5.3 assistant 专名专项抽取

整个会话的 assistant 发言合并后调一次 LLM（`ASSISTANT_FACTS_PROMPT`）。
只抽 **assistant 主动介绍的具体信息**——专有名、标题、链接、价格、
教学性知识（"Hoop Dance 是由熟练舞者表演的传统舞蹈"）——因为后续问题
可能问「你之前提到过哪个 X」。明确不抽：让用户**做选择**的选项列表
（菜单、A 或 B）；用户的复述；祝贺语。上限 12 条。

这一路存在的原因：single-session-assistant 题型考的就是「assistant 说过
的细节」。公开数据里 Mem0 系统把 assistant 事实设为一等公民后该题型涨
51.8 个百分点——这是所有公开系统最普遍的失分点。

### 5.4 会话内去重

对候选列表按「分词后拼成一个字符串」做键去重：同一会话里逐字重复的事实
只留一条。注意这是**词面精确去重**，不做语义判断——跨会话的复述合并
留给下一步的关系分类。

### 5.5 时间解析（规则优先，模型回退）

见第 6 节完整规则表。每条候选得到一个 `有效区间 [start, end)`。

### 5.6 写入期对齐：相似检索 + 关系分类 + 确定性执行

1. **相似检索**：新候选事实 vs 库内所有 active 事实做 BM25 检索，
   每个候选取 top-3 相似旧记忆（`min_score=1.0`）。
2. **关系分类**：把「旧记忆列表（编号 e1、e2...）+ 候选列表（编号
   c1、c2...）」一起发给 LLM，每个候选输出一个动作对象。
3. **确定性执行**：按动作对象改写存储（见 4.3 / 5.7）。

关键设计：检索是**逐候选**的（每个候选只看到与自己相似的旧记忆），不是
把全部旧记忆塞给 LLM。候选挂错合并目标的概率因此显著下降。

## 6. 时间解析：完整规则表

函数 `resolve_when_expr(原文, 会话日期)`，把用户的相对时间表述换成
`[start, end)` 区间。按以下顺序匹配，命中即返回：

| 输入（小写后） | 输出 | 说明 |
|---|---|---|
| recently / lately / a while ago / some time ago / not long ago | **None（拒绝解析）** | 模糊词不许猜日期，锚定到陈述日的任务交给下游 |
| `YYYY-MM-DD` | [该日, 该日+1) | 点估计 |
| `N days ago` / `N weeks ago` | [会话日期-N天, +1) | 点估计 |
| `N months ago` / `a month ago` | [会话日期减 N 个月（保留日号）, +1) | **月末钳制**：1 月 31 日减一个月是 2 月 28 日，不产生 2 月 31 日 |
| `N years ago` | [会话日期减 12N 个月, +1) | 点估计 |
| yesterday / today / tonight / just | 对应单日 | |
| next month / next week / last week | 对应区间 | 区间语义只给「未来计划」和「周」，不给 ago 类 |
| last month | [上月 1 日, 本月 1 日) | 唯一的 ago 类区间：自然月有明确边界 |
| last year | [去年 1/1, 今年 1/1) | |
| `December 2023` / `in December` | 该自然月 [1 日, 次月 1 日) | 年份推断规则：月号 ≤ 当前月 → 今年；> 当前月 → 去年（记忆默认过去） |
| `2023` | [2023-01-01, 2024-01-01) | |

两条总原则（各有失败案例背书）：

1. **相对距离表达一律给点估计**（[那天, 那天+1)），不给区间。教训：
   「N months ago」曾解析成 [月初, 会话日)，区间的两个端点都被当时长
   计算使用，结果差出近一个月。
2. **合法性校验**：解析结果必须落在 [会话日期 − 400 天, 会话日期 + 60 天]
   之内，否则视为解析失败（拦截 LLM 幻觉出的离谱日期）。规则解析失败时
   才用 LLM 输出的时间字段再走一遍同样的规则与校验。

## 7. 查询期流程

### 7.1 解析层

输入问题与提问日期，LLM 输出一个 JSON 查询计划
（`PARSE_PROMPT_V2`）。字段逐个解释：

| 字段 | 含义 | 示例 |
|---|---|---|
| `intent` | 查询意图，8 选 1：agg_count（计数）/ agg_sum（求和）/ fact_current（现值）/ fact_at_time（时刻值）/ list_events（事件列表，排序题专用）/ argmax（最值）/ lookup（查 assistant 说过什么）/ unknown | agg_count |
| `topic` | 5–15 词的富检索短语，供 BM25 模糊匹配。刻意要求「富」——「pre-1920 American coin collection how many I have」比「coins」召回好得多 | |
| `category` | 25 类之一或 null | plant |
| `count_kind` | 计数语义：events（从独立事件数出来）/ stated_total（记忆里有声明过的总数）/ either（不确定）/ none | |
| `window_days` / `month` | 时间窗口 | 31 / "2023-04" |
| `at_text` / `before_text` | 时刻查询的日期表述 / 排序比较的锚事件原文 | |
| `entities` | 问题预设存在的名词（供守卫层做存在性检查） | ["Shinjuku", "apartment"] |

提示词里有明确的意图分配规则，其中两条是踩坑换来的：
「Which came first / 排序」必须走 list_events，**永远不许**走
fact_at_time（后者只返回单条，答不了先后）；「哪个花得最多」走 argmax。

### 7.2 确定性执行器（按 intent 路由）

输入是 7.1 的查询计划，输出是一段带标签的文本（不是答案，是**供 reader
参考的计算结果**）。

**公共前置**：如果问题含 "before X"（X 是某事件），先定位 X 的日期，
把窗口设为 [远古, X 日期)，且意图强制改为 list_events（排序题统一走
事件列表）。另补一个「边界之后的事件」上下文分区——教训：「陈述时已
拥有」类事实的获取日期早于陈述日，硬窗口会把它切掉。

| intent | 处理 | 输出的关键内容 |
|---|---|---|
| agg_count / agg_sum | 候选事件生成（见下）→ 渲染 top-15（带相关分）→ `TOTAL MATCHED = N` 明确标注这是**召回计数不是答案**，要求 reader 逐条核对剔除不相关项 → agg_sum 附带「有数值事件的试探求和」 | 候选列表 + 计数提示 |
| list_events | 同上候选 → 额外输出按 valid_from 升序的**时间线块**（v3.3-P4：BM25 分数序对「哪个先」类问题是误导性的） | 时间线 |
| fact_current / fact_at_time | 取该 (subject, predicate) 的版本链 → current() 或 value_at(t) → 若问题像在问总量，附**算术注记**：声明总量 + 后续增量 → 「当前 37+1=38」。38 这个数在对话原文里从未出现，是代码算出来的——这是超出全上下文基线的独有增益 | 版本链 + 算术注记 |
| argmax | 候选事件抽数值，按数值降序渲染，首项高亮 | 排序表 |
| lookup | BM25 top-10 事实句直出 | 事实列表 |
| unknown | 不做确定性执行，直接走后面召回 | — |

**候选生成**（`_event_candidates`）双路合并：主路 BM25 检索 topic 取
top-30；辅路「category 命中但 BM25 低分」的事件给 0.6 底分保进候选——
防止精确类目命中被词面差异挤出。

**one-hop 实体扩展**（v3.9.1，仅 `store>100 events` 且 intent ∈
{agg_count, agg_sum, fact_current}）：

1. 惰性构建**实体倒排索引**：每个 active 事件的事实句分词（≥3 字符、
   去通用词表），得到「词 → 事件列表」的映射。
2. 取主候选 top-5 的**稀有实体**（该词在库内出现于 ≤8 个事件，越稀有
   越有区分度），通过倒排找到共现事件，最多补 12 条。
3. 渲染成独立的 `ONE-HOP RELATED` 段落，**不计入** TOTAL MATCHED——
   不锚定、不隐藏，由 reader 自行取舍（v3.1 教训）。
4. 效果：S 档（122k token、每题 723 事件）下，BM25 词面匹配漏掉的
   集合成员（如「朋友家的隔离缸」「第 4 个电影节」）被拉进上下文。
   S 档配对实验：该改动配合路由修正贡献 +16.7pp。

**状态一致性（v3.14）**

- 派生索引的缓存键 = `(事件数, active 数)`。新增、演化、遗忘归档都会改变这两个
  数之一，所以索引不会指向已归档事件；不再依赖 `write()` 里的手动失效
  （`store.add_event()` 与 `forget()` 都会绕过它）。
- `before_text` 的相对时间锚定到**问题日期**。旧实现写死 `2023-06-01`，
  `before_text="today"` 会把「今天」算成 6/1（实际问题日期 3/2，差 3 个月）。

**运行时选项（v3.16）**

- 全部开关收在 `memory_sys/options.py` 的 `RuntimeOptions`（frozen dataclass）：
  `premise_proper_only`、`enable_arith`、`enable_excerpts`、`enable_floor`。
- 取值优先级：`FusionMemory(options=...)` > 环境变量（`ABL_*`、`PREMISE_PROPER_ONLY`）> 默认值。
- 为什么不用模块全局：`fusion.py` 用扁平导入（`from render import RenderMixin`），
  `import memory_sys.render` 与管道里的 `import render` 是**两个模块对象**；
  v3.11 的 A/B 审计因此把开关设到了没人读的那份上，得出「0 题变化」的假结论。
  现在开关属于实例，两个实例可以并存不同配置，单测直接锁住互不影响。

**查询期分层（v3.17）**

| 方法 | 行数 | 职责 |
| --- | --- | --- |
| `read()` | 8 | 编排：初始化 trace → `_plan()` → `_render()` → 记 `elapsed_ms` |
| `_plan()` | 19 | 问题 → 查询计划（走 `parse` / `parse_zh` 缓存），写 `plan / plan_issues / parse_ms`，设 `last_meta` |
| `_render()` | 70 | 计划 → 执行 → 渲染，写 `execute_ms / execution / deterministic_result`，拼装事实清单 / 台账 / 偏好 / 摘录 / 地板 |
| `_guard_sections()` | 45 | 三道守卫（SCOPE NOTE / 推荐提示 / 前提校验），纯规则、不调模型，可脱离 LLM 单测 |

拆分前 `read()` 124 行，解析、执行、渲染、守卫混在一起，任何一段出错都只能整段重跑。
拆分是**纯移动**：500 题确定性上下文指纹 0 漂移，`elapsed_ms` 口径不变（仍在 read 出口计时）。

**跨平台确定性（v3.18）**

- 日期一律走 `textutil._fmt_d` 手工格式化（`f"{y:04d}-{m:02d}-{d:02d}"`），
  不用 `strftime`：`%Y` 对 1000 年以前**不保证补零**（glibc 出 `1-01-01`，
  MSVC 出 `0001-01-01`）。查询窗口下界常用 `datetime.min`，用 `strftime`
  会让同一份缓存在 Linux 与 Windows 上渲染出不同文本，回归基线在 CI 上判漂移。
- `splits` 的性质测试改为**合成实例**驱动（6 题型 × N 题），不再依赖
  `ref/` 里 15 MB 的评测集；真实数据的形状校验保留为 `skipif`，本地有则跑。

**对外接口（v3.21）**

内部是 `write(session, date)` / `read(question, date) -> str`：`read` 返回的是
给 LLM 的上下文，不是答案，计划与候选只能从 `last_trace` 侧门读。facade
`memory_sys/api.py` 把对外动作收敛成五个：

| 动作 | 方法 | 返回 |
| --- | --- | --- |
| 写入 | `add_session(turns, date)` | 新增事件数 |
| 检索 | `recall(question, date)` | `Recall(context, plan, sections, candidates, stats)` |
| 作答 | `answer(question, date)` | `Answer(text, recall, latency_s)` |
| 遗忘 | `forget(ttl_days / capacity / compact_days)` | 逐条归档原因 |
| 观测 | `stats()` / `save_cache()` / `reset()` | 规模与配置 |

约束：`llm` 只需 `.chat(prompt, max_tokens=...)`；`answer()` 在无 `llm` 时抛
明确错误；日期与 turns 在入口做校验并给出可用示例。内部模块不承诺稳定，
扩展优先走 `RuntimeOptions` 与 `Memory` 的方法。

**词表分层（v3.19）**

- `lexicon.LANGUAGE_GENERIC`（86 词）：代词、助动词、疑问词、量词、时间单位、
  通用指代——任何英文语料都成立，可硬编码。
- 语料专属的高频名词（容器容量、居住类型、学历、课程名…）**默认不在核心表里**，
  由 `RuntimeOptions.domain_terms` / `DOMAIN_TERMS` 环境变量按数据集注入。
  判据是「删掉它、换个数据集还能不能工作」。
- 顺手修了一处守卫精度问题：复合词的存在性判断原先「任一部词出现即算存在」，
  于是用户说过 20 加仑，`30-gallon` 里的 `gallon` 就能顶替数字，漏报真前提错误。
  现在**数字必须原样出现**，非数字部词仍按任一存在（保留 `art-related` 的宽松）。
- 500 题确定性上下文指纹 **0 漂移**；`audit_leakage.py` 的 P6 项归零。

### 7.3 BM25 检索：算法直白解释

BM25 是一个给「文档」按「与查询词的相关度」打分的公式。本项目自实现的
版本（`memory_sys/bm25.py`，无第三方依赖）参数 k1=1.5、b=0.75。

打分前先**分词**（`tokenize`）：转小写 → 按 `[a-z0-9]+` 切词 → 去停用词
（the/my/is 等高频虚词）→ 轻量词形折叠（lilies→lily、lugs→lug）→
同义词归并（bought/purchased→buy、birth→born、kids→child——这些是评测
中实际出现的表述差异）。

分数由三个因素相加而成，逐个解释：

| 因素 | 含义 | 直白效果 |
|---|---|---|
| IDF（逆文档频率） | `log(1 + (N-c+0.5)/(c+0.5))`，N 是文档总数，c 是含该词的文档数。一个词出现在越少的文档里，IDF 越大 | 查询里的「cucumber」比「plants」值钱——前者更稀有，命中它的文档更可能是答案 |
| 词频饱和（k1） | 词在文档里出现 f 次的贡献是 `f*(k1+1)/(f+k1*长度归一)`，f 增大贡献趋于饱和 | 一个词出现 3 次比 1 次分高，但出现 30 次不会无限涨（防止长篇重复刷分） |
| 长度归一（b） | 文档越长，同样词频的得分被压得越低 | 短事实句和长故事在同等命中下得分可比 |

为什么用 BM25 而不是向量检索：本项目的记忆规模（Oracle 每题约 33 条
事实）用 BM25 完全够用，且它是纯 Python、零依赖、可离线复现。向量检索
是 S 档正式化的下一步（接口已预留），试点阶段 BM25 + 地板已够用。

### 7.4 近逐字证据层（v3.6）

触发条件：intent 是 lookup 或 unknown（实测 single-session-assistant
56/56、single-session-preference 30/30 全部走这两个意图，覆盖率 100%）。

动作：对证据层全部轮次做 BM25，取**最强命中的 1 条轮次**，全文引用
（上限 1500 字符），渲染为 `[VERBATIM SOURCE TURN]`。

原理：single-session 题的答案逐字躺在一个轮次里，摘录（句子级、260
字符）是有损的。事实层压缩，源轮次引用保真——「记忆 ≠ 压缩」。
v3.7 曾试验把该层扩展到 fact_current 路由，三轮无正证据已回滚。

### 7.5 确定性守卫层（完整判定规则见第 8 节）

三个守卫按固定顺序挂载在渲染末尾：SCOPE NOTE / RECOMMENDATION HINT
（二选一）→ PREMISE CHECK。

### 7.6 渲染组装顺序

最终上下文由以下段落**固定顺序**拼接（每段有标签头）：

| 顺序 | 段落 | 内容 | 截断 |
|---|---|---|---|
| 1 | DETERMINISTIC QUERY RESULT | 7.2 的计算结果 | — |
| 2 | RELEVANT EXCERPTS | assistant 轮次先取 top-6，再在轮次内做句子级 BM25 取 top-8 句（教训：轮次级截断只露出长故事开头，细节在深处） | 每句 260 字符 |
| 3 | VERBATIM SOURCE TURN | 7.4 | 1500 字符 |
| 4 | DETERMINISTIC ORDINAL LOOKUP | 问题含「第 N 项」（正则 `\d+(st|nd|rd|th)`）时，用正则 `^\s*N[.):]` 在证据原文中直接定位列表第 N 项 | 220 字符 |
| 5 | CURRENT-STATE LEDGER | 有版本历史的槽位列表：`subject.predicate: CURRENT = ... (effective 日期; N 个旧值被替代)`——只列发生过 superseded/invalidated 的槽位 | 每条 180 字符 |
| 6 | PREFERENCES & OPINIONS | predicate=preference 的事实单独成段前置 | 每条 240 字符 |
| 7 | FACT MEMORY | 其余 active 事实按时间排序全列 | 上限 80 条 |
| 8 | USER STATEMENTS | **全部** user 轮次原文（地板） | 每轮 240 字符 |
| 9 | 守卫注记 | SCOPE NOTE / RECOMMENDATION HINT / PREMISE CHECK | — |

顺序是实验结果：偏好分段前置（v3.8）使 SS-P 从 81.11 提到 90.00——
偏好类软信息混在事件事实里会被稀释。

2375 token/题（上下文 2331 + 作答 44）。

## 8. 确定性守卫层：完整判定规则

守卫层解决两类失败：**该拒答时硬答**（`_abs` 题型）和**顺着问题的假
前提作答**。全部判定是 Python 代码，无 LLM 参与。

### 8.1 SCOPE NOTE（拒答措辞协议）

触发条件：解析层抽出的 entities（长度 >2 的词）在记忆库中**全未命中**。
命中判定（`_mentions`）：某个实体的**全部分词**出现在同一句事实或同一轮
发言里才算命中——只查单词会在库内任何位置出现，会被菜名「Italian-Style
Lentil Curry」这类部分命中骗过（v2.3 教训）。

触发后输出标准拒答句式，明确要求：用 "The information provided is not
enough. You did not mention ..." 作答，**禁止**以 0 或任何数字收尾。
背景：7 道语义正确的拒答曾被 judge 判错，因为模型输出 "the count is 0"
而判分语料期望 "information not enough" 措辞。

### 8.2 RECOMMENDATION HINT（建议类问句的分支）

如果命中 8.1 的触发条件、但问题属于**建议/推荐/征求意见形态**（关键词
表：any advice / can you recommend / should i / what do you think /
whether to / i'm trying to decide 等 18 项），则**不发拒答协议**，改发
推荐指引：「这是推荐请求不是事实查询，基于用户已陈述的兴趣与历史行为
推荐，不要以『从未提到该物品』为由拒绝」。

原理：这类问题的前提本来就不是「用户说过这个词」。v3.8 审计发现 SS-P
拒答型失分的主体是 "should I buy a NAS" 形态——旧豁免表漏了这些词。
`_abs` 全部 30 题对该词表零命中（扩展零回归）。

### 8.3 PREMISE CHECK（专名级假前提校验）

SCOPE NOTE 只在解析层 entities 全 miss 时触发，覆盖不了两种情形：实体
被 assistant 闲聊误命中（讲长野交通时罗列了 Shinjuku → "Shinjuku" 在
库内出现 → SCOPE NOTE 不触发，但用户从没说过自己住 Shinjuku）；问题
自带库内完全没有的假前提（"my 30-gallon fish tank"，用户说的是 20 加仑）。

判定规则（`_premise_check`，按顺序）：

1. 建议形态 → 直接返回 None（不校验）。
2. 构建 **user 语料**：全部 user 轮次原文 + 非 assistant 来源的事实句。
   注意**只扫 user 语料**——assistant 的提及不算「用户说过」。
3. 找**可疑专名**（两类信号）：
   - 词组级（2-gram / 3-gram）：组内含**硬专名信号**的词——原文大写且
     非句首（"How" 句首大写不算，v3.4.3 教训）、含数字（30-gallon）、
     含连字符（art-related）。组内各词若都在 user 语料出现则该词组视为
     存在；否则把其中的非通用词记为可疑。
   - 单词级：含数字或连字符且长度 ≥4 的词。连字符复合词按**部词**判定
     存在（"art-related" 的 art 在 user 语料即算存在——部词在说明
     修饰对象存在，v3.4.4 教训）。
4. 通用词表（`_GENERIC_TOKS`，约 90 词：how/many/current/month/tank/
   gallon 等）永远不构成可疑词。教训链：同义改写（acquire↔bought）不是
   假前提；"两词全专有" 会把 "acquire in" 这种措辞组合误报——只有
   **不可改写的专名**（Shinjuku、30-gallon、Porsche、Pete）才是校验对象。
5. 可疑词存在时，在 user 语料里找**最近邻词**（长度差 + 前缀匹配计分）
   一并输出。
6. 输出 `[PREMISE CHECK]` 段：列出从未在用户发言中出现过的专名 + 用户
   实际说过的近似词 + 指令「若前提不成立，按信息不足作答并指出用户实际
   说的内容，不要顺着假前提回答」。

效果：`_abs` 子集从 17/30 提到 24/30 且三轮逐题不差；S 档配对中
Shinjuku/30-gallon/Pete/Porsche 四道触发题全部翻对。

## 9. 遗忘与生命周期（memory_sys/lifecycle.py）

独立模块，默认关闭（Oracle 档没有记忆损失实验），经
`FusionMemory.forget()` 三行委托接入。三条确定性策略：

| 策略 | 判定 | 处理 |
|---|---|---|
| TTL | 事件的 `valid_to` 已闭合且失效时间超过 `ttl_days` | 归档 |
| 容量 | active 事件数超过 `capacity` | 按**重要性分**从低到高归档。重要性 = 佐证轮次数 + 数值完备性 + 新近度 |
| 历史压缩 | 同槽位存在更新的 active 值、且老版本（superseded/invalidated）陈述时间超过 `compact_days` | 归档老版本 |

**软归档语义**：被归档的事件 `status = archived`，退出「当前有效事实」
召回（`active_events` 不再返回它），但 `value_at(t)` 不过滤 archived——
历史时刻的值仍可查、仍可审计。这符合手册 B.1「历史版本保留方式」的要求。
幂等：重复执行不产生新归档。每次调用返回逐条归档原因。

## 10. 评测流水线

### 10.1 分层抽样（run_eval.py）

直接取数据集前 N 题会抽到单一题型（数据按题型排序存放，前 20 题全是
temporal-reasoning）。分层抽样算法：

1. 把全部题目按 `(题型, 是否拒答题)` 分桶。
2. 每桶配额 = `min(桶内题数, max(1, round(N × 桶内题数 / 总题数)))`。
3. 每桶内用固定种子（seed=42）的随机采样取出配额。
4. 配额取整导致总数偏离 N 时，随机增删补齐。
5. 按题目 id 排序输出。

### 10.2 断点续跑与缓存落盘

每题完成即写盘（hyp 行 + 缓存条目）。中断后重跑：已完成的题命中缓存
直接跳过，只跑剩余题。三类调用缓存（抽取 ext| / assistant asst| /
关系 rel|）按内容寻址独立失效——换答题模型不动管线缓存，改解析提示词
只重采样解析层。

### 10.3 判分

`judge.py` 直接 import 官方仓库的 `get_anscheck_prompt`（不重写判分
提示词），把「问题 + 标准答案 + 系统答案」交给判分模型输出 yes/no。
实测成本 222 token/题。

### 10.4 方差来源（重要）

| 方差源 | 实测大小 | 应对 |
|---|---|---|
| 服务端非确定性（temperature=0 仍存在） | 基线两次运行 37/500 题翻转，±1.4pp | 基线与系统各跑 2 次以上，报均值±标准差 |
| 管线多级 LLM 调用放大 | fusion ±1.5–2pp | 同上 |
| 确定性守卫层钉住拒答方向 | v3.4.5 收窄到 ±0.31 | ——这是确定性组件的副收益 |
| 缓存重采样（改任一提示词 → 该层缓存全失效） | 单次 ±1.5pp | 改动前先评估换血成本 |
| 判分模型误判 | 判错集合中约 64% 为语义误判 | 语义审计剥离；正式口径待官方 judge 复跑 |
| 小样本噪声 | 20 题冒烟 ±18pp | 冒烟只验证管线不坏；结论只看全量或多轮均值 |

**判定纪律**：单次差值 <3pp（双方方差之和）不下结论；改动保留需要
「配对翻转 + 机制解释」双重证据。

## 13. 术语表

| 术语 | 定义 |
|---|---|
| LLM | 大语言模型，接收文本输出文本的函数，本系统通过 HTTP API 调用 |
| token | 模型处理文本的最小单位，约 0.75 个英文单词，计费按 token 数 |
| prompt | 发给 LLM 的完整输入文本 |
| temperature | 采样随机度参数，0 = 每步取最高概率词 |
| JSON / JSONL | 结构化文本格式 / 每行一个 JSON 对象的文件格式 |
| 缓存 | 按「提示词版本 + 输入哈希」存取的 LLM 调用结果，避免重复付费 |
| BM25 | 按词频、逆文档频率、文档长度给「文档与查询的相关度」打分的检索算法 |
| IDF | 逆文档频率，一个词出现的文档越少越有区分度 |
| 停用词 | the/is/how 这类高频虚词，检索前过滤 |
| 原子事实 | 不可再拆分的一条陈述，本系统的事实载体是完整句子 |
| 双时间轴 | 事实有效时间（τ_v）与陈述时间（τ_t）两条独立的时间戳 |
| 演化（evolve） | 状态更新，旧值到锚点前曾为真（只封有效轴） |
| 更正（correct） | 宣布旧值从未为真（两轴都封，历史时刻也查不到） |
| 槽位（Slot） | 同一 (主体, 关系) 的事件版本链 |
| 基数（cardinality） | 谓词允许同时为真的值个数；1=单值可演化，2=多值可累加 |
| 拒答（abstention） | 证据不足时回答「信息不足」而非硬给一个值 |
| 假前提 | 问题里预设了用户从未陈述过的事实（如「我在 Shinjuku 的公寓」） |
| 守卫层 | 查询期渲染末尾的确定性判定段（拒答协议/前提校验/推荐指引） |
| 地板（floor） | 全部 user 轮次原文照进上下文，保证检索完全失败时信息不丢 |
| one-hop 扩展 | 通过稀有实体共现把主候选的语义关联事件补进上下文 |
| reader / judge | 答题模型 / 判分模型 |
| Oracle / S / M | 基准的三个难度档（证据已筛 / 122k 干扰 / 中等） |
| pp | 百分点（percentage point），85% 到 86% 是 +1pp |
| McNemar 检验 | 对同一批样本前后配对翻转次数的统计显著性检验 |
| 消融（ablation） | 关掉单个机制跑全量，量化该机制的真实贡献 |
