#### 2026-09-29 · v3.0 诊断：MS 27 道错题归因（全量 fusfull2）

| 类别 | 数量 | 实例 |

| judge 噪声/存疑 | 3 | `gpt4_7fce9456` 答案数值与 gold 一致（4=four）仍判错 |
| BM25 召回缺失 | 1 | `gpt4_ab202e7f` matched=0，靠地板兜底仍差 1 |

**根因**：v2.5 把 strict/borderline 双层改成"TOTAL MATCHED(召回大数) + 读者排除"是**减法心智**——
"3 盆植物"匹配 46 条（min_score=0.5 太松 + 类别辅路兜底），读者从 46 的噪声里手动数，误差 ±1。
v2.4 的双层方向本身正确，错在 borderline 被埋没。

**决策（v3.1）**：恢复双层，改为**加法心智**——
- STRICT（≥ max(0.45×best, 1.5)）：程序算死 `STRICT COUNT`，作为答案锚点
- BORDERLINE（中分，≤12 条显式列出）：指令"从 STRICT COUNT 出发，逐一检查 borderline，属于的加上"
- LOW（其余）：不渲染，只报数量
- agg_sum 附每事件金额提示（`_first_number`），并给 STRICT 子集的 tentative sum

#### 2026-09-29 · v3.1 全量验证：回归，回滚 ❌

**全量 500：85.40%（427/500），比 v2.6 的 86.80% 掉 7 题。**

| 题型 | v2.6 | v3.1 | Δ |
|---|---|---|---|
| multi-session | 79.70% (106) | 75.19% (100) | **-6** |
| temporal-reasoning | 85.71% (114) | 83.46% (111) | **-3** |
| KU | 88.46% (69) | 91.03% (71) | +2 |
| SS-U | 94.29% (66) | 97.14% (68) | +2 |
| SS-A | 94.64% (53) | 92.86% (52) | -1 |
| SS-P | 86.67% (26) | 83.33% (25) | -1 |

**根因（回滚后复盘）**：
1. **锚定效应**：STRICT COUNT 漏掉真事件时（BM25 词面差异），读者被程序给出的数字锚死——
   art-events 题 strict=3，读者直接答 3（gold 4，volunteering 在 borderline 里没被加上）；
2. **LOW 层隐藏**：v2.6 平铺 top-15 里低分真事件可见，v3.1 把它们藏了——
   TR/MS 里相关但词面弱匹配的事件（"volunteered" vs "attended"）从此不可见。

**教训**：①20 题冒烟 80% 是假信号——n=20 的 CI（±18pp）盖不住 ±1.4pp 的真实回归，
冒烟只能验证"管线没坏"，不能验证"渲染策略更优"；②给读者的确定性数字必须
**要么完全正确，要么明确标注不可信**——半权威的锚点比没有锚点更糟；
③v2.6 的召回大数 + "这是 RECALL 不是答案"的诚实标注，反而给了读者正确的先验。

**决策：回滚到 v2.6 渲染**（代码已还原，含注释记录失败机理）。
fusfull2 的 86.80% 仍是当前代码状态的权威实测——回滚后渲染与 v2.6 逐字节等价，
不再重跑。v3.1 的全量数据保留在 `results/fusfull3-*` 作反例存档。

**下一方向修正**：MS ±1 计数误差的正解不在渲染层（两种渲染都试过了），
而在**写入期**——把"同一现实世界事件的多会话提及"（计划→发生→后续）在关系分类中
更可靠地合并，从源头减少重复事件。这属于 KU 演化强制化方向的延伸。

| # | 根因 | 实证 |

| 1 | **同批候选从不互相比对**：关系分类只做"候选 vs 已有记忆"，同一会话多轮复述的同一事件以 paraphrase 形式全部落库 | sourdough 面包同一事件 5 个变体（"tried out a new bread recipe" / "On Tuesday, I used my sourdough starter" / "tried a sourdough bread recipe"…全部 valid_from=05-16，同一会话） |

"over-merging destroys countable events"警告，批内版保留并加强。

#### 2026-10-03 · v3.2 实现 → 全量回归 → 回滚 ❌

**A（批内 dedup）**：RELATION_PROMPT 新增 `dedup` action（同批候选互相折叠）+ `_classify` 解析 `cN` 目标与链式重定向 + `_apply` 落库跳过。
**B（subject 过滤）**：agg 意图 `_event_candidates(user_only=True)`，事件行加 `(assistant)` 标签。
**C（kind 指引）**：agg_count 指令明确"只数 user 的完成动作，排除计划/状态/assistant 建议"。

| 实验 | 结果 | 分析 |
|---|---|---|
| v3.2（A+B+C）冒烟 | 70% (14/20) | `2ce6a0f2` 被弄坏：**2 月的 art 事件在写入期被过度折叠**（Women in Art 展览、volunteering 全消失）；`gpt4_93159ced_abs` 槽位漂移（Wunderlist 无关槽位顶上）→ **A 的证据链充分：dedup 过度合并**。B/C 的渲染指令本身工作正常 |
| v3.2.1（回滚 A，留 B+C）冒烟 | 55% (11/20) | 表面暴跌，但逐题检查：5 道"新坏"里 ≥2 道**judge 噪声**（`gpt4_21adecb5` 答案正确被判错、`gpt4_93159ced_abs` 语义正确被判错）。冒烟噪声 > B/C 预期收益，必须全量裁决 |
| **v3.2.1 全量 500** | **84.60% (423/500)，-2.2pp** | 27 损 16 修，净 -11。受损集中在 TR ×10、MS ×12、_abs ×4 |

**根因（本节最重要的一条发现）**：v3.2.1 的关系分类是**全新采样**（PROMPT_VERSION 换代 → rel 缓存 key 全换 → 全部 LLM 关系调用重跑）。逐题对比显示 43 题换血（27+16），其中相当部分是**关系分类方差**——同一 prompt 下 evolve/new/merge 的判定摇摆会级联改变整个事件池和槽位聚类。
**也就是说：v2.6 的 86.80% 与 v3.2.1 的 84.60% 之间有相当部分是"关系分类这一高方差操作的采样方差"，而非 B/C 改动的真实效应。**

**结论与教训**：
1. **回滚全部三个改动**（代码已与 v2.6 逐字节等价，`results/fusfull321-*` 留作存档）；
2. **关系分类是系统最大的方差源**：任何触碰关系调用的迭代，全量分数波动 ±1.5–2pp 属于采样噪声——**没有固定 seed 的 LLM 流程，"改进"必须显著大于方差才可信**（B/C 的理论收益 ~+1pp < 方差）；
3. 写入期事件合并（A）在 LLM 单次调用判断 paraphrase 的形态下**不可行**——过合并（art 事件消失）与漏合并（sourdough 5 变体）并存，且错误不可逆地破坏了下游全部层（事件池→槽位→BM25→算术注记）。若要重做，方向应该是**确定性规则**（同日期+词面 Jaccard 阈值）而非 LLM 判断；
4. 冒烟阶段 judge 噪声率约 10%（2/20），20 题分数 ±10pp 不可信——今后冒烟只做"管线健康检查 + 明确回归定位"，**策略优劣一律全量裁决**。

**当前权威口径：v2.6 = 86.80%（434/500）。**

**下一方向（吸取本轮教训）**：写死边界，只做低方差改动——
- 官方 judge 复跑（消除 judge 噪声后重新归因，_abs 的真实水平才能看清）；
- 消融矩阵（关算术注记/关 BM25 回退跑全量——注意关系缓存全部复用 v2.6 的，只动读取侧，零方差源）；
- MS ±1 的正解改为**确定性批内去重**（同日期 + 词面 Jaccard ≥ 0.6 折叠，代码规则不进 LLM）。

2. **C 的 rel 缓存级联击穿**：evolve 改变 _active_events → 后续会话 rel 键全变 → 关系重采样。且缺 kind 守卫（Jaccard 0.45 会把"两场不同比赛"合并——v3.2 过合并同构）→ C 降级为**条件 GO**（kind=state 硬守卫 + 全量翻转审计过门槛），本轮暂缓；
3. **验证计划无统计功效**：三改动目标题合计增益上限 ~1.4pp，永远过不了 3pp 阈 → 改为**配对逐题翻转分析**（共享缓存、≥3 reader 运行、目标题须全翻对、原对题多数翻错即回滚）。
4. **更简修法**：SS-A 枚举、抽取幻觉、截断三类错共享一个底层事实——确定性层的数值缺 verbatim 原文佐证。**"数值事实必附源句"一个机制治三类**，比三个新机制便宜。

**修订后执行序**：B 收敛版（读取期枚举索引+相对序数+多列表消歧+数值事件附源句）→ A 改道版（正则窗口锚）→ C 暂缓（过审计门槛再做）。

## 竞品时间开销分析：腾讯 Hy Memory 2.0（2026-10-26）

**架构（公开资料：GitHub README / 官网 / 第三方实测）**
- 三层开源：Hy-Memory-30B-A3B（30B 总参、3B 激活，专用记忆写入模型）、
  hy-memory SDK、MemHub 应用。
- 三场景：chat（L0–L7 分层：raw / fact / summary / profile / schema /
  intention）、working（fact + experience 双层）、coding（再加零 LLM 的
  diff 版本链）。
- 写入链：embed + raw → LLM extraction → reconcile（supersedes，
  旧记录保留可追溯）→ vector store / graph store。
- 三模式：lite=仅原文 embedding，零 LLM；pro=抽取 + reconcile；
  ultra=再加 System 2（schema induction，由 evolve() 显式触发，不随
  add 自动运行）。存储：ChromaDB/Qdrant/FAISS + Kuzu/Neo4j + SQLite。

**时间数据（口径必须分开）**
- lite 第三方实测：写入 110–120 ms/条（首条含初始化 0.76 s）；
  检索 3–20 ms；更新 10 ms。零 LLM 调用。
- 官方口径：写入速度「大幅领先同类」；1.0 时代「与 Mem0 同档、
  Graphiti 的 8 倍」（无绝对值）。
- pro / ultra 无公开延迟数字——不能把 lite 的 110 ms 当成可比起点的
  效用档。

**与 fusion 对比（本机实测）**
- Oracle：写入约 20–25 s/题（14–17 次串行调用 × 约 2 s），read p95 11.3 ms。
- S 档：写入约 14 min/题（约 344 次调用），read 86 ms。
- 差距来源排序：① 写入粒度（我们每 user 轮一次 LLM，Hy 每 add 一次）；
  ② 调用种类（抽取 + assistant 专项 + 关系分类）；③ 模型部署（远程
  glm-5.2 API vs 本地 3B 激活模型）。
- 结论：绝对开销 Hy 更低（lite 低两个数量级；pro 预计 2–4 倍，无官方
  数字）。在「不换 LLM、不提并发」约束下可追的只有粒度：批量抽取 +
  assistant 合并 + 关系分块，预计 Oracle 7–9 s/题、S 3–5 min/题（3–4 倍）。
  lite 的 100 ms 级不可达——那等于放弃抽取与协调。

## Hy-Memory 2 若用来跑 LongMemEval：开销核算（2026-10-26）

**先定标（本地实测 `longmemeval_s_cleaned.json`）**
- 500 题，每题一座独立记忆库：p50 **122,456 tokens**（p10 119k / p90 125k，极窄），
  平均 47.7 个 session、493.5 轮、约 49 万字符；全量 **61.2 M tokens**。
- 题与题之间零复用 → 写入成本必须按「每题 × 全量 haystack」计，
  任何跨会话复用红利在这个 benchmark 上都不存在。
- session 级 add 总次数 ≈ 500 × 47.7 = **23,850 次**（turn 级 246,750 次）。

**lite 档（零 LLM）：实测 11 s/题，500 题约 1.5 h**
- SDK 本体（hy-memory 2.0.5，mode=lite，chroma 后端）在本机**首个 add 即
  segfault（exit 139）**，faiss 后端未装成（Python 3.13 无 wheel），
  故改用等价流水线：同 bge-m3 端点、同 add 粒度（1 session = 1 次 embed）、
  热连接。chroma upsert 51 条 < 0.5 s，可忽略。
- 实测（qid ec81a493，51 sessions / 12.8 万 tokens）：写入 **11.0 s**，
  per add 均值 0.22 s（p50 0.21 / p95 0.26）→ 约 0.09 s/k tokens。
  usage 字段返回 24,964 tokens 明显低于字符数折算（≈128k），该端点
  token 计数不可信，按字符/4 计。
- 折算平均题（47.7 session）：**10.5 s/题** → 500 题 **≈ 1.5 h**。
- 但 lite = 纯向量召回，无抽取/无版本/无聚合；其自报 85.20% 不可能出自
  lite（同口径它把 mem0 测到 47.00%）。lite 的 1.5 h 买到的是 RAG 级分数。

**pro / ultra 档：与 fusion 同量级，官方口径更慢**
- 官方「端到端写入 12.3 s / 1k tokens」（未标注档位与硬件）→
  122k tokens × 12.3 = **25 min/题** → 500 题串行 **≈ 210 h（8.7 天）**；
  8 并发约 26 h。
- 若自托管其 30B-A3B（3B 激活）：按 500-token 分块 ×1.5 次调用/块
  ≈ 367 次/题 × 2 s ≈ **12 min/题** → 500 题 **≈ 100 h**。
- ultra 再加 `evolve()` 的 schema 归纳与跨域清扫，按 +20–50% 计：
  **120–310 h**；且每题独立库时 L3–L7 画像层没有积累空间，清扫器收益最低。
- 写入 token 量级：pro 需把 61.2 M tokens 原文过一遍 LLM，含分块 prompt
  开销约 **80–150 M 输入 tokens**；lite 为 61.2 M embedding tokens。

**与 fusion 同口径对比**
| 方案 | 写入/题 | 500 题串行 | 依据 |
| --- | --- | --- | --- |
| Hy lite | 10.5 s | 1.5 h | 本机实测（embedding 主成本） |
| Hy pro（官方口径） | 25 min | 210 h | 12.3 s/1k tokens |
| Hy pro（本地 30B） | 12 min | 100 h | 367 调用 × 2 s，估算 |
| Hy ultra | 14–38 min | 120–310 h | pro ×1.2–1.5，估算 |
| fusion Oracle | 22.5 s | 3.1 h | 本机实测，6.6k tokens/题 |
| fusion S | 14 min | 117 h | 本机实测，344 调用/题 |

- 读侧：fusion S 实测 p50 2.31 s / mean 3.16 s（含答题），Hy lite 检索
  3–20 ms + 一次答题调用，两者读侧都不是瓶颈。
- **结论**：档位决定一切（lite 与 pro 差 70–140 倍）。要复现其 85.20%
  必须开 pro/ultra，此时开销与 fusion S 档同量级（100–210 h vs 117 h），
  按官方口径反而更贵；「8× 加速」是相对 Graphiti，不是相对本系统。
  benchmark 的「每题一座新库」结构正好抹掉了 Hy 的跨会话/多 agent 优势。

## infra-2026-11 · 阶段 E：上下文回归基线 + 读侧缓存诚实性（2026-11-05）

**自选方向**：仍不碰写入成本、不追分数。动机来自前四轮反复出现的一件事——
每次改动后都要临时写几行 Python 去比「500/500 是否逐字相同」，口径（是否归一
空白、比哪些字段、怎么算一致）随手改，很容易自欺。本轮把口径固化成工具，
并顺带审计了一个此前被默认忽略的前提。

### 工具：`scripts/regress.py`

指纹字段（全部可复现，不含任何耗时）：

| 字段 | 含义 |
| --- | --- |
| `plan` | 查询计划（intent / topic / entities / 时间字段） |
| `ctx` | 确定性结果归一空白后的哈希 |
| `sections` | 渲染段落标题顺序 |
| `cand` | 候选事件（日期 / 事实 / 分数） |
| `one_hop` / `matched` | 一跳扩展条数 / 召回条数 |
| `chars` | 上下文原始字符数（识别「只改格式」） |

- `--update` 写基线，`--check` 比对；有语义漂移 / 题号增减 → **退出码 1**。
- 子集回放（`--ids`）时，基线里未回放的题不计为漂移，便于定点复核。
- `--prev-trace` 给第一处漂移打印文本 diff。
- `--dump-cache` 只导出本次真正命中的缓存键，生成精简夹具。
- `--drop-parse` 生成去掉 parse 键的缓存副本（见下节的诚实性审计）。

`scripts/replay_trace.py` 抽出 `select_instances` / `replay_records` 供复用，
CLI 行为不变。

### 验证

- **500 题基线**：回放 8s，命中缓存键 7365 个（等于缓存条目总数，说明没有
  任何条目是死重）；`--check` **语义漂移 0 / 格式漂移 0 / 缺失 0 / 新增 0**，
  退出码 0。基线文件 `results/golden-oracle500.json`（114 KB）。
- **跨进程**：另起进程再跑一次，仍 0 漂移（上一轮修掉的 one-hop 排序问题
  没有复发）。
- **负向对照**：手工篡改基线里一题的 `ctx`，`--check` 报
  `SEMANTIC ... ['ctx']`、退出码 1 —— 工具不是橡皮章。
- **单测**：15 题代表性子集（6 题型 × 7 intent，含 1 道拒答、1 道历史计数
  错题、1 道 one-hop 漂移题）做成**自包含夹具**：题面/会话/日期 gzip 193 KB
  + 340 键缓存 203 KB，不依赖 `ref/` 里 15 MB 数据集，因此 CI 里也真跑而不是
  跳过。新增 2 个单测：基线逐字段一致、parse 键复算命中。单测 53 → **55**，
  全绿 0.84s。

### 读侧缓存诚实性审计（本轮真正的新发现）

`read()` 的 parse 也走缓存，所以回放的「500/500 一致」只能证明
**「同一份计划 → 执行 / 渲染 / 上下文」没有漂移**，不能证明 `_parse` 的改动
无害。此前几轮把它当成端到端等价，是过度解读。

做法：取 8 题，用 `--drop-parse` 删掉它们的 parse 键，`run_eval --ids` 真实
重跑（16 次调用：8 解析 + 8 作答），再 `--check` 对基线：

```
比对 8 题：语义漂移 3 / 仅格式漂移 0 / 缺失 492 / 新增 0
  SEMANTIC b9cfe692      [temporal-reasoning] 变动字段: ['plan', 'ctx']
  SEMANTIC ba358f49      [multi-session]      变动字段: ['plan']
  SEMANTIC gpt4_2655b836 [temporal-reasoning] 变动字段: ['plan', 'ctx']
```

- **5/8 计划逐字段相同**；3/8 只在 `topic` / `entities` 的措辞上不同
  （如 `"my new car"` → `"new car"`、`["Rachel","wedding"]` →
  `["friend Rachel"]`），`intent` / `category` / 时间字段 **0 变化**。
- 其中 2 题上下文跟着变：`b9cfe692` 15828 → 15635 字符（-193），
  `gpt4_2655b836` 15046 → 15039（-7），`matched` 都是 14——变化来自
  BM25 排序，不是召回集合。
- 对 `b9cfe692` 连打 3 次（temperature 已为 0）结果 **3/3 一致**；带
  `seed=42` 也 3/3 一致。说明差异不是「每次调用随机」，更像**缓存里冻结的
  旧模型输出 vs 当前模型快照**的差异。

**结论与边界**：历史分数用的是缓存里的旧计划，口径自洽；但「重跑一遍应该
一模一样」这个假设不成立。以后报方差、做配对，必须注明基线日期与模型版本；
验证解析类改动必须走 `--drop-parse` + 真实调用，不能拿回放当证据。

### 判定

**保留，无回滚，无行为变化**（500/500 与基线一致）。生产仍是
**v3.8（Oracle）/ v3.9.1（S 档）**，`infra-2026-11` 不占用 v3.10 编号。

**下一步**：① 提交前先跑 `pytest tests/ -q`（15 题基线在 CI 里真跑）；
500 题 `regress --check` 仍需要本地 `ref/` 数据集，作为发版前的最后一道闸；
② 解析类改动固定用 `--drop-parse` 小样本（8–12 题即可暴露措辞漂移）；
③ 若要压方差，先量化「同题重复解析的计划一致率」，再决定是否值得为解析
加约束解码——本轮不做，因为没有证据表明白花这个成本能换来分数。

## infra-2026-11 · 阶段 I：前提校验的形态误伤（2026-11-05）

**自选方向**：上一轮提议做「filter → distinct → count」的算子代数。按"先查再改"

  —— 那正是 v3.10a/c 被试错的做法。

### 一、量化：守卫在非拒答题上净伤害

| 分组 | 触发 | 该组准确率 | 未触发组 | 差 |
| --- | --- | --- | --- | --- |
| 非拒答（470） | 91 | 84.6% | 90.5% | **-5.9pp** |
| 拒答（30） | 11 | 81.8% | 68.4% | +13.4pp |

守卫对 `_abs` 是正收益（设计如此），对非拒答题则是净伤害——两件事必须分开看。

### 二、根因：普通动词被当成"专名前提"

守卫的 3-gram 判定要求"至少一个硬专名信号"（大写/数字/连字符），但**收集
suspects 时把 gram 里所有非常用词都收进去**。于是 `catch with Alex` 这个
gram 因为有 `Alex` 而通过阈值，最终 suspects 里却混进了动词 `catch`；
用户说的是 `caught`（形态不同），就被判成"假前提"，整题被迫拒答。

### 三、修法：suspects 只报带专名信号的词

`render.py` 增加 `PREMISE_PROPER_ONLY`（默认开启）：收集时记录每个 suspect
是否来自大写/数字/连字符词，最后过滤。**只减少 suspects，不新增**，所以
结构上不可能让原本不触发的题开始触发。

- 非拒答：触发 **91 → 36**（55 题不再触发；其中 46 题原本答对、9 题原本错）

## infra-2026-11 · 阶段 J：SCOPE NOTE 不再强制拒答（2026-11-05）

### 一、先否决一个候选：类别硬过滤

追 3 道"召回缺失"题（matched=1 金标 2）时发现 `_execute` 对 `agg_*` 用
`e.category == plan.category` **硬过滤**：

- `21d02d0d`：3/26 那场 5K 的 category 是 `event`，plan 是 `activity` → 被过滤；
- `6d550036`：两个项目都是 `education`，plan 是 `work` → 全被过滤，只剩一个
  `work` 干扰项。

看起来该删，但先量化（189 道 agg/list 题）：**170 道有候选被过滤，其中 142 道
当前答对**；"过滤后只剩 ≤2 条"的 46 道里 41 道答对。删掉过滤会把大量干扰项
放回去，风险远大于收益。**否决**，只记录机制（真正的毛病是解析给的 category
偶尔错，不是过滤本身）。

### 二、SCOPE NOTE 的伤害面（500 题零调用）

| 分组 | 触发 | 该组准确率 | 未触发 | 差 |
| --- | --- | --- | --- | --- |
| 非拒答（470） | 19 | **57.9%** | 89.1% | **-31.2pp** |
| 拒答（30） | 5 | 100% | 76.0% | +24.0pp |

触发它的 entities 绝大多数是**普通名词**：`siblings`、`current role`、
`internet plan`、`occupation`、`college`、`relatives`。用户其实说过
"one brother and three sisters"，只是没说过 "siblings" 这个词。

原文措辞是强制性的：`you MUST answer using wording like "The information
provided is not enough" … do NOT give a number`。于是**词汇不匹配 = 强制拒答**。

### 三、改法：先找同义表达，真缺才拒答

```
[MEMORY SCOPE NOTE] The memory contains no verbatim statement about: X.
The user may have described it in different words (e.g. 'siblings' as
brother/sister, 'internet plan' as its speed or provider) — check the facts,
preferences and verbatim user turns for a paraphrase before concluding.
Only if the information is genuinely absent, answer with wording like
"The information provided is not enough ..." — do NOT invent a number or a fact.
```

只改这一段的措辞，不新增/删除任何段落，也不动 `entities` 的产生逻辑。
